## 2. 담당한 업무와 구현 내용

### 고객용 서비스 화면 구현

- Figma 디자인을 바탕으로 홈·활동지 탐색·상세·장바구니·주문·프로필 등 고객 화면을 구현하고 실제 API 데이터를 연결했습니다.
- 하단 내비게이션에 현재 선택된 탭 표시와 아이 변경 문구를 추가해 위치와 동작을 이해하기 쉽게 보완했습니다.
- 작은 글씨, 줄바꿈, 썸네일 문구 중복, 결제 동의 영역 등 화면에서 발견한 사용성 문제를 수정했습니다.
- 모바일 중심 화면을 PC에서도 사용할 수 있도록, 왼쪽 브랜드 소개와 오른쪽 고정 폭 앱 화면으로 구성한 반응형 레이아웃을 구현했습니다.
- PC에서는 앱 영역 내부 스크롤과 하단 메뉴 고정을 적용하고, 작은 화면에서는 브랜드 영역을 숨기도록 했습니다.

### 회원가입·인증·프로필 연결

- 이메일 회원가입·로그인과 소셜 로그인 흐름을 연결하고 인증 실패 상황의 안내를 보완했습니다.
- 신규 가입 이후 부모 정보와 아이 정보 입력으로 이어지는 흐름을 구성했습니다.
- 이름·닉네임·아이와의 관계·부모 연령대 저장을 연결하고, 서버의 `profile_completed` 값으로 입력 미완료 계정을 안내하도록 했습니다.
- 닉네임의 길이·허용 문자·공백 규칙을 서버 명세와 맞추고 프로필 편집에서도 수정할 수 있도록 했습니다.
- Access 토큰 만료 시 갱신과 재요청을 처리하고, 고객과 관리자 인증 정보를 분리했습니다.
- 회원 탈퇴 화면을 실제 DELETE API와 연결해 서버 성공 이후에만 세션을 정리하도록 했습니다.

### 아이 정보·활동지 탐색

- 아이 정보 등록·수정·삭제·선택 API와 관심 놀이 카테고리 데이터를 연결했습니다.
- 고객 화면의 카테고리 이름과 서버 분류 이름이 달라 필터가 일치하지 않는 문제를 별칭 매칭으로 보완했습니다.
- 활동지 상세에 구매 전 샘플 이미지 API를 연결하고, 유료 PDF 다운로드와 샘플 조회를 구분했습니다.
- 하·중·상 난이도를 `easy`, `normal`, `hard`와 일치시켰습니다.
- 데이터가 없는 추천 조건과 미구현 기능은 실제로 작동하는 것처럼 처리하지 않고 준비 상태를 안내했습니다.

### 주문·결제·PDF 이용 흐름

- 장바구니, 결제 예상 금액, 주문 생성, 결제 승인, 결제 내역 및 상세 조회를 연결했습니다.
- 소장과 7일 이용권 선택이 견적 요청과 주문 생성에 동일하게 전달되도록 구성했습니다.
- 금액은 화면에서 임의로 확정하지 않고 서버의 견적·주문 응답을 기준으로 사용하도록 했습니다.
- 구매 권한이 있는 활동지에는 다시 구매하도록 안내하는 대신 다운로드 화면으로 이어지게 했습니다.
- 주문번호 표시·복사와 결제 내역 썸네일 보완으로 고객 문의에 필요한 정보를 확인하기 쉽게 했습니다.
- 새 명세의 주문일·결제일·환불일·결제 수단을 연결하고 한국 시간으로 표시했습니다.
- 최근 1·3·6개월·1년·전체 기간 조회를 연결하고 월말 날짜 보정을 구현했습니다.
- 백엔드가 생성한 회원별 발급 코드 PDF를 열람·저장하도록 연결했습니다. PDF 코드 생성·인쇄 엔진 자체는 백엔드 담당입니다.
- PDF를 이미 받아 둔 Blob으로 저장해 불필요한 추가 파일 요청을 피하도록 수정하고 회귀 테스트를 추가했습니다. 서버 집계까지 포함한 다운로드 횟수 문제의 최종 해결은 별도 확인 대상입니다.

### 관리자 콘솔 구현

- 고객 서비스와 별도로 접근하고 배포하는 관리자 프론트엔드를 구성했습니다.
- 관리자 권한을 서버에서 확인하고 일반 회원의 접근 오류를 처리하도록 했습니다.
- 학습지·카테고리 등록, 상품 수정, 표지·PDF 업로드, 미리보기 이미지 관리 API를 연결했습니다.
- 비공개 포함 학습지 목록과 상세 조회를 연결하고 공개 상태·카테고리·검색어·페이지 필터를 적용했습니다.
- 비공개 파일은 일반 이미지 주소만 넣어서는 열 수 없어, 관리자 인증 헤더로 요청한 뒤 Blob URL로 표시하도록 구현했습니다.
- 주문·환불·회원 관련 제공 API를 연결하고 API가 없는 관리 기능과 구분했습니다.
- Chart.js 기반 매출 대시보드에 일·월·연 집계, 결제 금액·환불 금액·순매출 데이터를 연결했습니다.
- 발급 코드 검색, 회원·활동지별 발급 이력, 다운로드 횟수와 상세 로그 조회를 연결했습니다.

### 배포·협업·문서화

- Cloudflare Pages에서 고객 사이트와 관리자 사이트를 각각 빌드·배포하는 구성을 마련했습니다.
- GoDaddy DNS와 Cloudflare 사용자 지정 도메인 연결을 진행하고 HTTPS 활성 상태를 확인했습니다.
- 로컬 개발과 운영 환경의 API 주소, CORS 허용 목록, OAuth 콜백 주소 문제를 구분해 백엔드 담당자와 협의했습니다.
- 사업자 정보와 서비스 정책 링크를 사이트 하단에 배치했습니다. 약관·환불 정책의 최종 법적 검토와 사업자 고지 확정은 별도 업무입니다.
- API가 있지만 연결되지 않은 기능과 API 자체가 없는 기능을 나누어 고객·관리자 화면을 점검했습니다.
- 기능별 요구사항, API 계약, 완료 기준, 우선순위, 실행 방법을 Markdown으로 남겨 다른 개발 환경에서도 이어서 작업할 수 있게 했습니다.

## 3. 자기소개서에 활용하기 좋은 문제 해결 사례

### 사례 A. 데이터를 받기 전에 ‘내역 없음’이 표시되는 문제

**문제**: 결제 내역이나 구매 목록에 진입하면 서버 응답이 오기 전에 빈 목록 안내가 나타나, 사용자가 자신의 구매 내역이 사라졌다고 오해할 수 있었습니다.

**해결**: 요청 중·실패·조회 성공·빈 결과를 구분하고, 로딩이 끝난 뒤에만 빈 화면을 표시하도록 수정했습니다. 장바구니·주문 상세·영수증·아이 목록에도 같은 원칙을 적용하고 공통 로딩 화면을 만들었습니다.

**설명할 역량**: 비동기 상태 관리, 사용자 관점의 오류 발견, 공통 UI 구성, 일관된 사용자 경험.

### 사례 B. API와 화면의 이름·상태가 달라 발생하는 연동 문제

**문제**: 화면에는 ‘숫자’가 있지만 서버 분류는 ‘수학’인 경우처럼, 이름 차이 때문에 기대한 검색 결과가 나오지 않았습니다. 주문 상태에서도 화면과 서버의 코드가 다른 항목이 있었습니다.

**해결**: 카테고리 별칭 매칭을 도입하고, 서버가 실제 허용하는 상태 코드와 난이도를 명세·응답 기준으로 맞췄습니다. 화면의 표시명과 요청 값을 분리해 처리했습니다.

**설명할 역량**: 데이터 계약 이해, FE·BE 간 원인 분석, 도메인 값 정규화, 회귀 검증.

### 사례 C. 비공개 학습지를 관리자도 조회하기 어려운 문제

**문제**: 공개 상품 API를 관리자 목록에서도 사용하면 비공개 상품이 빠집니다. 비공개 파일은 단순 `<img src>`로 요청할 경우 관리자 인증 헤더가 전달되지 않습니다.

**해결**: 백엔드와 관리자 전용 목록·상세·파일 계약을 맞추고 새 API에 연결했습니다. 파일은 인증 요청 후 Blob URL로 표시하고, 화면 종료 시 URL을 해제하도록 했습니다.

**설명할 역량**: 권한에 따른 API 분리, 인증 파일 처리, 리소스 정리, 운영 도구의 요구사항 이해.

### 사례 D. 결제 옵션과 주문 데이터의 일치

**문제**: 소장·기간제 상품을 같은 구매 화면에서 다룰 때, 화면에서 고른 옵션과 서버 견적·주문 생성의 옵션이 어긋날 가능성이 있었습니다.

**해결**: 이용권 선택을 동일한 식별자 목록으로 견적과 주문 생성에 전달하고, 이전 옵션의 견적 응답을 현재 결제에 사용하지 않도록 상태를 구분했습니다. 계약 테스트로 두 요청의 일치를 검증했습니다.

**설명할 역량**: 결제 흐름의 정합성, 비동기 응답 관리, 서버 기준 금액 처리, 중요한 경계의 테스트.

### 사례 E. 개발 완료 범위를 명확하게 전달

**문제**: 화면이 있어도 API가 없거나 데이터가 저장되지 않는 기능이 섞여 있으면 팀이 실제 완료 상태를 판단하기 어렵습니다.

**해결**: 고객·관리자 화면을 함께 조사하고, 연결 가능한 기능은 구현했습니다. 서버 개발이 필요한 기능은 22개 항목의 요구사항·완료 기준·의존성으로 정리했습니다. 새 명세가 도착하면 완료 상태와 검증 대상을 갱신했습니다.

**설명할 역량**: 요구사항 분석, 범위 관리, 기술 문서화, 협업과 인수인계.

## 4. 바로 활용할 수 있는 자기소개 문장

### 짧은 소개

React와 TypeScript를 활용해 고객 서비스와 관리자 도구를 함께 구현하며, 화면 구현부터 API 연동과 배포까지 경험한 프론트엔드 개발자입니다. YIPPEE CLUB 프로젝트에서 회원가입, 활동지 탐색, 주문·PDF 이용 흐름과 관리자 운영 기능을 연결했습니다. 사용자가 실제로 겪는 문제를 찾아 수정하고, API 계약과 검증 기준을 문서로 남기는 개발 방식을 지향합니다.

### 프로젝트 경험 중심

YIPPEE CLUB은 부모가 아이에게 맞는 놀이 활동지를 찾아 구매하고 PDF로 이용하는 서비스입니다. 저는 고객용 웹과 관리자 콘솔의 프론트엔드 구현 및 API 연동을 중심으로 참여했습니다. Figma 디자인을 React·TypeScript 화면으로 구현하고, 회원·아이 정보, 장바구니, 소장·기간제 주문, 결제 내역과 PDF 이용 흐름을 연결했습니다. 관리자에서는 학습지 등록과 비공개 상품 조회, 매출 대시보드, 발급 코드 이력 조회를 구현했습니다. 특히 조회 전에 빈 결과가 나타나는 문제를 공통 로딩 상태로 개선하고, 인증이 필요한 비공개 파일은 Blob 방식으로 처리했습니다. 백엔드 담당자와 데이터 필드와 오류·권한 규칙을 맞추고 기능별 완료 기준을 문서화하며, 실제 사용과 운영을 함께 고려하는 경험을 쌓았습니다.

### 문제 해결 역량 중심

저는 화면이 표시되는 것에서 멈추지 않고, 사용자가 기능을 끝까지 이용할 수 있는지 확인하려고 합니다. YIPPEE CLUB에서는 결제 내역을 불러오는 동안 ‘내역 없음’이 먼저 보이는 문제를 발견했습니다. 요청 중·실패·빈 결과를 분리하고 공통 로딩 화면을 적용해 조회 상태를 명확하게 전달하도록 개선했습니다. 또한 고객과 관리자 화면을 점검하며 API가 있는 미연결 기능과 서버 개발이 필요한 기능을 구분했습니다. 연결 가능한 기능은 구현하고, 나머지는 요구사항과 완료 기준으로 문서화했습니다. 이 경험을 통해 사용자 경험뿐 아니라 API 계약, 예외 처리, 협업 과정까지 함께 살피는 개발 습관을 만들었습니다.

## 5. 이력서·포트폴리오용 요약

- React·TypeScript 기반 고객 웹 및 관리자 콘솔 구현, Figma 디자인 반영과 PC·모바일 반응형 구성.
- 회원·아이·활동지·주문·PDF 이용 API 연동 및 비동기 로딩·오류·빈 상태 처리 개선.
- 관리자 학습지·매출·발급 이력 API 연결, 인증이 필요한 비공개 파일의 Blob 표시 구현.
- Cloudflare Pages 고객·관리자 분리 배포 구성과 사용자 지정 도메인 연결.
- API 계약 테스트 및 고객·관리자 타입 검사·배포 빌드 검증, 기능명세·인계 문서 작성.

## 6. 확인 가능한 검증 결과와 표현 주의점

작성 시점 기준 고객·관리자 TypeScript 검사, 자동 테스트 **27개**, 고객·관리자 Pages 빌드가 통과했습니다. 테스트 수는 저장소 전체의 현재 수치이며, 모든 테스트를 한 사람이 처음부터 작성했다는 뜻은 아닙니다.

- 최근 부모 추가정보·주문 날짜/기간·관리자 비공개 파일 연결과 PC 레이아웃은 아직 커밋·푸시 전입니다. 마지막 확인된 develop 푸시는 `3eb0b3c`입니다.
- 최신 관리자 조회와 실제 부모 정보 저장은 로그인 후 통합 확인이 남아 있습니다. 실결제·환불 전체 흐름을 최종 검증했다고 표현하지 마세요.
- 토스 시크릿 키 발급이나 프론트 연결을 결제 심사 승인·운영 결제 안정화 완료와 동일하게 표현하지 마세요.
- PDF 고유코드의 서버 생성·인쇄, 데이터베이스 설계, Spring API 구현 전체를 프론트 담당 성과로 쓰지 마세요. 요구사항 협의와 FE 연동으로 설명할 수 있습니다.
- 실시간 검색어 집계, 배지 자동 지급, 사진 인증, 성장 리포트, 리뷰, 쿠폰·캐시 등의 전체 기능을 완성했다고 쓰지 마세요. API 미지원과 후속 개발 항목이 남아 있습니다.
- 성능 향상률, 매출 증가, 사용자 수, 전환율, 장애 감소율은 측정 자료가 없어 기재하지 않았습니다.
- 코딩 도구나 AI를 활용한 범위는 면접에서 실제 작업 방식대로 설명하고, 본인이 판단한 요구사항·검증·수정 내용을 구체적으로 말하는 것이 좋습니다.

## 7. 제출 전 직접 채울 내용

- 프로젝트 참여 기간, 팀 규모, 본인의 정확한 담당 범위.
- 가장 깊이 이해하고 직접 설명할 수 있는 문제 해결 사례 1~2개.
- 지원 직무에 맞춰 강조할 부분: UI 구현 / API 연동 / 운영 도구 / 협업·배포.
- 구현 화면 캡처, 관련 코드·커밋 링크, 가능하다면 검증 전후 화면.
- 위 초안을 자신의 표현으로 정리하고, 직접 하지 않은 작업이나 아직 확인하지 않은 성과는 제외.
