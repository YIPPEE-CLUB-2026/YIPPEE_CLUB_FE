# YIPPEE CLUB 프로젝트 경험 정리

## 1. 프로젝트 개요

YIPPEE CLUB은 부모가 아이의 연령과 관심사에 맞는 놀이 활동지를 찾아 구매하고 PDF로 이용하는 웹 서비스입니다. 고객용 웹과 관리자 콘솔의 프론트엔드 구현, 백엔드 API 연동, 배포 환경 구성과 기능 점검을 중심으로 진행했습니다.

주요 기술: React, TypeScript, Next.js, React Router, CSS, Chart.js, REST API, Git/GitHub, Cloudflare Pages.

협업 방식: Figma 디자인 확인, Swagger와 Markdown API 명세 대조, 백엔드 개발자와 필드·권한·오류 규칙 협의, 개발 요청서와 인계 문서 작성.

## 2. 핵심 역량 도출

지원 공고 원문이 없으므로, 첨부 예시의 역량 분류에 실제 프로젝트 경험을 매칭했습니다.

| 순번 | 핵심 역량 | 프로젝트에서 확인되는 경험 | 자기소개서 어필 포인트 |
|---|---|---|---|
| 1 | 문제 해결 능력 | 조회 전에 빈 결과가 표시되는 문제, 카테고리 불일치, 비공개 파일 조회 문제 분석 및 수정 | 화면의 증상에서 데이터와 요청 흐름까지 추적해 원인을 구분하고 개선한 경험 |
| 2 | AI 도구 이해 및 활용 능력 | AI 코딩 도구를 활용한 구현·코드 점검·API 비교·테스트·문서 정리 | 요구사항을 구체화하고 생성된 결과를 명세와 실제 화면으로 검증한 경험 |
| 3 | 협업 및 의사소통 능력 | 백엔드 담당자에게 API 추가·수정 사항 전달, 최신 명세 수령 후 연동, 인계 문서 작성 | 필요한 데이터와 완료 기준을 구체적으로 전달해 FE·BE 사이의 차이를 줄인 경험 |
| 4 | 웹 시스템 및 배포 이해 | 고객·관리자 분리, 토큰 인증, CORS·OAuth 콜백·DNS·HTTPS 설정 점검 | 개발 화면부터 API 통신과 배포 환경까지 연결해서 이해한 경험 |
| 5 | 자기주도적 학습 및 기술 적용 | Figma 기반 반응형 구현, 매출 차트, 인증 파일 Blob 처리, 공통 로딩 화면 구성 | 서비스 요구사항에 필요한 기술을 찾아 적용하고 검증한 경험 |

## 3. 핵심 역량별 경험 및 STAR 정리

### 3.1 문제 해결 능력 — 조회 상태와 빈 결과 구분

**경험 요약**

결제 내역에 들어갔을 때 실제 응답을 받기도 전에 ‘아직 결제 내역이 없어요’가 표시되는 현상을 확인하고, 비슷한 조회 화면까지 함께 수정했습니다.

| STAR | 내용 |
|---|---|
| S · 상황 | 결제 내역과 구매 목록에서 초기 빈 배열이 실제 조회 결과처럼 표시되고 있었습니다. 사용자는 구매 기록이 없거나 사라졌다고 오해할 수 있었습니다. |
| T · 과제 | 서버 응답 전 상태와 실제 빈 결과를 분리하고, 다른 조회 화면에서도 같은 문제가 발생하지 않도록 일관된 처리가 필요했습니다. |
| A · 행동 | 요청 중·성공·실패 상태를 구분하고 조회 완료 후에만 빈 결과를 표시하도록 수정했습니다. 결제 내역·주문 상세·영수증·구매 목록·장바구니·아이 정보에 적용하고 공통 로딩 화면을 구성했습니다. |
| R · 결과 | 데이터를 기다리는 동안 로딩 상태를 보여 주고, 완료 후 결과나 빈 목록을 표시하도록 개선했습니다. 오류가 발생했을 때 빈 목록 안내가 함께 표시되는 문제도 보완했습니다. |

**자기소개서 활용 문장**

결제 내역을 조회할 때 서버 응답 전에 빈 목록 안내가 먼저 표시되는 문제를 발견했습니다. 초기 데이터와 조회 결과를 같은 상태로 처리하고 있는지 확인한 뒤, 요청 중·성공·실패를 분리했습니다. 이후 장바구니와 구매 목록 등 유사 화면에도 같은 원칙을 적용했습니다. 이를 통해 비동기 데이터 처리에서는 결과뿐 아니라 결과를 기다리는 과정도 사용자 경험의 일부라는 점을 배웠습니다.

**추가로 정리할 근거**

- 수정 전후 화면과 해당 상태 처리 코드.
- 동일한 문제가 있었던 화면의 범위.
- 실제 사용자 피드백이 있다면 그 내용. 시간 단축률이나 만족도는 측정 자료가 있을 때만 추가.

### 3.2 AI 도구 이해 및 활용 능력 — 구현과 검증에 활용

**경험 요약**

AI 코딩 도구를 활용해 화면 구현, API 명세 비교, 수정 작업과 문서화를 진행하고 실제 요구사항과 맞는지 반복적으로 확인했습니다.

| STAR | 내용 |
|---|---|
| S · 상황 | 고객 사이트와 관리자 콘솔을 함께 개발하면서 화면 구현뿐 아니라 API 연결 여부, 오류 처리, 배포 상태까지 확인할 필요가 있었습니다. |
| T · 과제 | AI 도구를 개발 보조에 활용하되, 제안된 코드나 설명을 실제 구현 완료와 혼동하지 않고 검증해야 했습니다. |
| A · 행동 | 디자인·오류 화면·API 명세를 바탕으로 수정 요구를 구체화했습니다. 결과를 화면에서 확인하고, 잘못 반영된 문구나 배치를 피드백해 수정했습니다. 구현 후 타입 검사·계약 테스트·빌드를 활용해 확인했습니다. |
| R · 결과 | UI 수정과 API 연동, 기능 점검 및 인계 문서 작성에 AI 도구를 활용한 경험을 쌓았습니다. 현재 저장소 기준 자동 테스트 27개와 고객·관리자 타입 검사·배포 빌드가 통과했습니다. |

**자기소개서 활용 문장**

프로젝트에서는 AI 코딩 도구를 구현과 점검을 돕는 수단으로 활용했습니다. 오류 화면과 API 명세를 제공해 수정 방향을 구체화하고, 결과가 의도와 다를 때는 실제 화면을 기준으로 다시 조정했습니다. 특히 코드가 생성됐다는 사실과 기능 검증이 끝났다는 사실을 구분하며 타입 검사, 계약 테스트, 배포 빌드 결과를 확인했습니다. 이 과정에서 도구를 활용하는 능력만큼 결과를 판단할 기준을 세우는 일이 중요하다는 점을 배웠습니다.

**추가로 정리할 근거**

- 본인이 직접 판단한 요구사항과 AI 제안을 수정한 사례.
- 생성된 코드의 동작을 직접 설명할 수 있는 범위.
- AI 도구 활용 경험이며 LLM 모델 개발, Document AI 제품 구현, AI 판독 서비스 운영 경험으로 표현하지 않음.
- 테스트 27개는 현재 저장소 전체의 수치이며, 모두 혼자 작성했다는 의미로 쓰지 않음.

### 3.3 협업 및 의사소통 능력 — API 계약과 완료 기준 정리

**경험 요약**

프론트 화면에 필요한 데이터가 API에 없을 때 요청 사항을 문서로 정리하고, 백엔드의 새 명세가 전달되면 이를 기준으로 연결했습니다.

| STAR | 내용 |
|---|---|
| S · 상황 | 부모 정보의 관계·연령대, 고객 주문 날짜·결제 수단, 관리자 비공개 상품 조회 등 화면에 필요한 기능과 기존 API 사이에 차이가 있었습니다. |
| T · 과제 | 프론트에서 임의의 값으로 채우기보다, 어떤 데이터와 동작이 필요한지 백엔드 담당자에게 명확히 전달해야 했습니다. |
| A · 행동 | 기존 API로 연결할 수 있는 항목과 서버 개발이 필요한 항목을 구분했습니다. 필요한 필드·요청/응답·권한·완료 기준을 정리해 전달하고, 최신 API 명세를 받은 뒤 부모 정보·주문 기간 조회·관리자 비공개 조회에 반영했습니다. |
| R · 결과 | 새 명세에 맞춰 프론트 연결을 진행했고, 남은 기능과 통합 확인 항목을 인계 문서로 남겼습니다. 구현 여부와 실제 검증 여부를 구분해 후속 작업자가 확인할 수 있도록 했습니다. |

**자기소개서 활용 문장**

백엔드와 협업할 때는 ‘이 기능이 필요하다’는 설명에서 그치지 않고 화면에 필요한 필드와 동작을 정리하려고 했습니다. 부모의 관계·연령대 저장이나 주문 날짜 조회처럼 기존 API로 구현하기 어려운 항목을 분리하고, 요청·응답과 완료 기준을 문서로 전달했습니다. 이후 최신 명세를 기준으로 프론트 연결을 진행하면서, 요구사항을 구체적인 데이터 계약으로 바꾸는 소통의 중요성을 배웠습니다.

**추가로 정리할 근거**

- 실제 전달한 개발 요청서와 수정된 API 명세.
- 본인이 제안한 항목과 백엔드 담당자가 구현한 항목의 구분.
- 협의 중 달라진 요구사항이나 의견 조율 사례.

### 3.4 웹 시스템 및 배포 이해 — 고객·관리자와 인증 환경 분리

**경험 요약**

고객 사이트와 관리자 콘솔의 배포 구성을 분리하고, API 인증과 브라우저 통신·도메인 문제를 점검했습니다.

| STAR | 내용 |
|---|---|
| S · 상황 | 로컬 개발 주소, 운영 도메인, 관리자 도메인이 달라 API 통신과 로그인 동작이 환경에 따라 달라질 수 있었습니다. |
| T · 과제 | 개발·운영 환경의 연결 조건을 맞추고, 고객과 관리자의 인증 및 배포 범위를 구분해야 했습니다. |
| A · 행동 | Cloudflare Pages의 고객·관리자 빌드 설정을 구분하고 GoDaddy DNS와 사용자 지정 도메인을 연결했습니다. CORS 허용 주소와 OAuth 콜백 주소를 점검하고, 관리자 권한 확인 및 토큰 저장 영역을 고객과 분리했습니다. |
| R · 결과 | 고객·관리자 도메인을 구성하고 HTTPS 활성 상태를 확인했습니다. 환경별 설정과 실행 방법을 문서화하고 양쪽 Pages 빌드를 검증했습니다. |

**자기소개서 활용 문장**

고객 사이트와 관리자 콘솔을 개발하면서 화면 코드 외에도 브라우저와 서버가 연결되는 조건을 이해할 필요가 있었습니다. 로컬과 운영 주소의 CORS 설정, 소셜 로그인 콜백 주소, DNS와 HTTPS 상태를 점검하고 고객·관리자 배포 구성을 분리했습니다. 이 경험을 통해 프론트엔드 개발도 인증과 배포 환경을 함께 이해해야 안정적으로 기능을 전달할 수 있다는 점을 배웠습니다.

**추가로 정리할 근거**

- 직접 설정한 부분과 다른 담당자에게 요청한 부분.
- 도메인·빌드 설정 문서 및 관련 커밋.
- Linux·Docker·Kubernetes를 사용했다는 근거는 이번 경험에서 확인되지 않으므로 추가하지 않음.

### 3.5 자기주도적 학습 및 기술 적용 — 관리자 비공개 파일 처리

**경험 요약**

관리자가 비공개 학습지의 표지·PDF·미리보기를 확인할 수 있도록 관리자 전용 조회와 인증 파일 표시 방식을 연결했습니다.

| STAR | 내용 |
|---|---|
| S · 상황 | 공개 API를 사용한 목록에서는 비공개 학습지가 보이지 않고, 일반 이미지 태그만으로는 파일 요청에 관리자 Authorization 헤더를 전달하기 어려웠습니다. |
| T · 과제 | 비공개 자료를 고객에게 공개하지 않으면서 관리자 화면에서는 조회할 수 있도록 해야 했습니다. |
| A · 행동 | 새 관리자 목록·상세 API를 연결하고, 파일은 관리자 토큰을 붙여 요청한 뒤 Blob URL로 표시하도록 구현했습니다. 화면 종료 시 URL을 해제하고 인증 실패 처리도 기존 API 계층과 연결했습니다. |
| R · 결과 | 비공개 파일을 다루는 프론트 처리 경로를 구성하고 인증 바이너리 응답과 권한 오류 계약 테스트를 통과했습니다. 실제 관리자 로그인 후 파일 열람에 대한 통합 확인은 남아 있습니다. |

**자기소개서 활용 문장**

관리자 기능을 구현하며 공개 이미지와 인증이 필요한 파일의 처리 방식이 다르다는 점을 확인했습니다. 관리자 전용 API를 연결하고 인증 헤더로 받은 파일을 Blob URL로 표시하는 방식을 적용했습니다. 또한 화면을 벗어날 때 리소스를 해제하고 권한 오류를 처리했습니다. 새로운 기술을 적용할 때는 화면 표시뿐 아니라 인증 조건과 리소스 수명까지 함께 살펴야 한다는 점을 배웠습니다.

**추가로 정리할 근거**

- 인증 파일 요청·Blob URL 생성·해제 코드.
- 계약 테스트와 실제 관리자 화면 확인 결과를 구분.
- 최종 통합 확인 후에는 실제 비공개 자료 열람 결과를 추가.

## 5. 심층 질문과 답변 정리

### Q1. 가장 막혔던 구간과 해결 방법은 무엇인가요?

화면에 문제가 보일 때 원인이 프론트 상태 처리인지, 서버 데이터 부재인지, 인증이나 환경 설정인지 구분하는 과정이 중요했습니다. 조회 화면에서는 초기 빈 배열이 실제 결과처럼 표시되는 문제를 상태 분리로 해결했습니다. 반면 주문 날짜처럼 기존 응답에 데이터가 없는 경우에는 프론트에서 값을 만들어 넣지 않고 필요한 필드를 백엔드에 요청했습니다. 먼저 원인의 범위를 구분한 뒤 코드 수정과 API 협의를 나눠 진행했습니다.

### Q2. 결과를 숫자로 설명할 수 있나요?

현재 확인 가능한 수치는 저장소의 자동 테스트 27개 통과와 고객·관리자 타입 검사 및 배포 빌드 통과입니다. 이는 검증 범위를 설명하는 근거이며, 개발 시간 단축률이나 사용자 만족도 향상률을 의미하지 않습니다. 별도 측정하지 않은 성과 수치는 넣지 않습니다.

### Q3. 이 경험을 지원 직무에 어떻게 적용할 수 있나요?

고객 환경의 문제를 다루는 직무라면 화면·네트워크·API 계약을 나눠 원인을 확인한 경험을 연결할 수 있습니다. 개발 직무라면 비동기 상태 처리, 인증 파일 처리, 계약 테스트를 강조할 수 있습니다. AI 활용을 요구하는 직무라면 요구사항을 구체화하고 결과를 검증하며 도구를 사용한 과정을 설명할 수 있습니다. 단, 실제 공고에 맞춰 강조점을 선택해야 합니다.

### Q4. 협업 과정에서 본인은 어떤 역할을 했나요?

고객과 관리자 화면에 필요한 동작을 정리하고 기존 API로 가능한 기능과 추가 개발이 필요한 기능을 구분했습니다. 백엔드에 필요한 데이터와 완료 기준을 전달하고, 새 명세를 받은 뒤 프론트에 연결했습니다. 최종 작성 시에는 이 중 본인이 직접 판단·작성·검증한 범위를 구체적으로 덧붙입니다.

### Q5. 아직 완료하지 못한 부분은 무엇인가요?

실시간 검색어 집계, 배지 자동 지급, 사진 인증, 성장 리포트 등은 서버 API가 없어 후속 과제로 남아 있습니다. 최신 API 연결의 실제 저장·비공개 파일 열람과 결제·환불 전체 흐름도 별도 통합 확인이 필요합니다. 완료된 코드 연결과 운영 검증을 구분해 설명합니다.

## 6. 자기소개서 통합 초안

저는 사용자 화면의 문제를 API와 데이터 흐름까지 연결해 살펴보는 개발자가 되고자 합니다. 부모가 아이에게 맞는 놀이 활동지를 찾아 구매하는 YIPPEE CLUB 프로젝트에서 고객 웹과 관리자 콘솔의 프론트엔드 구현 및 API 연동을 중심으로 참여했습니다.

개발 과정에서는 결제 내역을 불러오기 전에 빈 목록 안내가 먼저 표시되는 문제를 확인했습니다. 요청 중 상태와 실제 빈 결과를 분리하고, 장바구니와 구매 목록 등 유사 화면에도 같은 처리 원칙을 적용했습니다. 또한 부모 정보와 주문 날짜처럼 기존 API에 필요한 데이터가 없을 때는 임의의 값으로 채우지 않고, 필드와 완료 기준을 정리해 백엔드 담당자에게 전달했습니다. 최신 명세가 전달된 뒤에는 부모 정보 저장, 주문 기간 조회와 관리자 비공개 자료 조회를 연결했습니다.

AI 코딩 도구는 구현과 점검을 돕는 수단으로 활용하되, 실제 화면과 API 명세를 기준으로 결과를 검토했습니다. 고객·관리자 타입 검사, 계약 테스트와 배포 빌드를 확인하고 미구현 기능은 별도 인계 문서로 남겼습니다. 이 경험을 바탕으로 요구사항을 구체화하고, 문제의 원인을 구분하며, 팀이 이어서 작업할 수 있는 결과를 만드는 개발자로 성장하고자 합니다.
