# 관리자 별도 배포 보안 및 BE 추가 요청 정리

작성: 2026-11-26 / 전달 대상: 준성님(BE 담당)

## 1. 이번 목표

관리자는 고객 사이트와 별도 앱으로 배포합니다.

| 구분 | 주소 | 현황 |
|---|---|---|
| 고객 | https://www.yippeclub.com | Cloudflare Pages 운영 중 |
| API | https://api.yippeclub.com/api/v1 | 개발 서버 배포 중 |
| 관리자 로컬 | http://127.0.0.1:3100 | 실제 로그인·API 연결 |
| 관리자 운영 | https://admin.yippeclub.com | 별도 Pages 프로젝트로 배포 준비 중, 아직 개통 완료 아님 |

**요구사항: 관리자 URL을 알아도 임의의 사용자가 관리자 화면·운영 데이터·관리 API에 접근할 수 없어야 합니다.**

주소를 숨기거나 프론트에서 버튼을 숨기는 것만으로 해결하지 않습니다. 관리자 웹 접근 제어와 BE API 권한 검사를 각각 적용합니다.

## 2. 접근 제어 권장 구조

```text
admin.yippeclub.com 접속
  → Cloudflare Access에서 허용된 운영자 이메일 인증
  → 관리자 앱 로그인
  → BE Access 토큰 발급
  → /api/v1/admin/* 호출 때 서버가 활성 상태와 관리자 권한 검사
```

### 2.1 관리자 웹 자체의 접근 제한 (Cloudflare 담당)

1. Cloudflare Zero Trust Access에 관리자 웹용 애플리케이션을 등록합니다.
2. `admin.yippeclub.com/*` 전체를 보호합니다. 첫 페이지뿐 아니라 정적 자산·하위 경로도 범위를 확인합니다.
3. Allow 대상은 승인된 운영자 이메일만 정확히 나열합니다. 기본 관리 이메일은 `yippeclub1@gmail.com`이며 추가 인원은 별도 승인합니다.
4. `Everyone`, 전체 `gmail.com` 도메인 허용은 사용하지 않습니다.
5. Google 로그인 또는 이메일 일회용 코드 등 조직에 맞는 인증 방식을 사용하고 세션 만료 시간을 정합니다.
6. 관리자 계정에 MFA를 적용할 수 있는 인증 공급자 정책을 권장합니다. 이메일 OTP를 MFA와 동일한 수준으로 표현하지 않습니다.
7. 다른 계정·로그아웃·시크릿 창으로 접근 거절을 직접 확인합니다.

**중요: 커스텀 도메인만 보호하고 Pages 기본 주소를 열어두면 화면 접근 제한을 우회할 수 있습니다.**

- 관리자 `프로젝트.pages.dev`, 브랜치/커밋별 Preview URL도 접근 제어 적용 여부를 별도로 확인합니다.
- Pages Preview 보호만 켰다고 Production 기본 주소까지 보호된 것으로 간주하지 않습니다.
- 가능한 제품 설정으로 모든 기본/미리보기 진입점을 보호하거나, 해당 주소의 배포 제공을 차단합니다.
- 단순 리다이렉트만으로 미리보기·정적 자산까지 보호됐다고 간주하지 않습니다. 직접 접근 테스트가 필요합니다.
- 필요 없는 Preview 빌드는 비활성화합니다.
- 운영 산출물에서 가상 로그인 HTML(`ui-preview.html`)은 제외합니다. 가상 로그인 플래그도 운영에서는 강제로 꺼집니다.

Cloudflare 대시보드의 정확한 기능 제공 범위에 맞춰 설정하며, 확인되지 않은 보호 상태를 '완료'로 표시하지 않습니다.

확인한 공식 안내:

- [Pages Preview 접근 보호](https://developers.cloudflare.com/pages/configuration/preview-deployments/)
- [Production pages.dev와 Custom Domain까지 Access 적용](https://developers.cloudflare.com/pages/platform/known-issues/)
- [외부 DNS로 Pages 커스텀 도메인 연결](https://developers.cloudflare.com/pages/configuration/custom-domains/)

### 2.2 관리자 API 권한 검사 (BE 담당)

모든 `/api/v1/admin/**`에서 아래를 서버가 검사해야 합니다.

- 서명·만료·토큰 무효화가 검증된 Access 토큰인지
- 해당 회원이 현재 활성 상태인지
- 현재 관리자 권한이 있는지 (`ADMIN_EMAILS` 또는 실제 관리자 역할 정책)
- 일반 회원은 403, 미인증 사용자는 401로 거절되는지
- 회원·주문·발급 이력뿐 아니라 등록·수정·환불·파일 변경 등 모든 하위 경로에 동일하게 적용되는지
- 프론트가 전달한 `is_admin`, 이메일, 회원 ID만으로 권한이 결정되지 않는지

Cloudflare Access 통과는 BE 관리자 권한을 자동으로 부여하지 않습니다. 고객 계정으로 로그인했다고 관리자 기능이 열려서도 안 됩니다.

공개 API 도메인에서 관리자 API에 직접 접근하는 것도 가능합니다. 따라서 브라우저 화면 접근 제한만으로 API를 보호하지 않습니다. `Origin` 헤더 역시 curl 등에서 임의 지정할 수 있으므로 신원 증명이 아닙니다.

### 2.3 Access 검증을 BE까지 확장하는 경우 (선택 설계, 별도 협의)

BE의 관리자 API 자체에도 Cloudflare Access 인증을 추가하려면 별도 설계가 필요합니다.

- 보호 대상 API 경로, Access 앱 audience, JWKS·issuer·만료 검증을 정의합니다.
- 전달된 Access JWT를 헤더 존재 여부만으로 신뢰하지 않습니다.
- 브라우저의 교차 출처 요청과 Access 세션·preflight 동작을 검토합니다.
- EC2 IP:8080 직접 접근으로 Access 검증을 우회할 수 없어야 합니다. 원본 접근 제한 또는 서버의 검증 강제가 필요합니다.
- 이를 위해 FE에 서비스 토큰이나 Client Secret을 넣지 않습니다.
- 고객 API까지 일괄 차단되지 않도록 `/admin/**` 범위를 분리합니다.

1차 배포는 '관리자 웹 Access 보호 + BE 관리자 토큰 검사'를 최소 기준으로 하고, API까지 Access를 요구할지는 협의해 주세요.

## 3. CORS 허용 목록 복구·추가 요청

2026-11-26 확인 당시 고객 로컬 `http://localhost:3000` 요청은 `403 Invalid CORS request`가 발생했습니다. 이전에는 관리자 3100이 허용된 것을 확인했고 실제 관리자 로그인도 사용자 테스트로 확인했습니다. 설정 변경 시 기존 출처가 누락되지 않게 아래 주소를 함께 허용해 주세요.

```env
CORS_ALLOWED_ORIGINS=https://www.yippeclub.com,https://yippeclub.com,http://localhost:3000,http://127.0.0.1:3000,http://localhost:3100,http://127.0.0.1:3100,https://admin.yippeclub.com
```

- 개발·운영 환경을 분리할 수 있다면 개발 서버에서 로컬을 허용하고 운영 서버에는 필요한 운영 주소만 둡니다.
- 임시 Pages 주소에서 테스트해야 하면 정확한 주소만 한시적으로 추가하고 이후 제거합니다. `*.pages.dev` 전체를 허용하지 않습니다.
- 메서드·`Content-Type`·`Authorization` 허용을 확인합니다.
- `X-Request-Id`가 브라우저에 노출되도록 기존 설정 유지.
- CORS는 API 권한 검사를 대체하지 않습니다.
- 환경변수 적용 후 재시작/재배포 및 실제 OPTIONS·POST 검증이 필요합니다.

## 4. 관리자 로그인 운영 기준

- 관리자 이메일 `yippeclub1@gmail.com`의 실제 가입·활성·관리자 권한은 확인 및 사용자 로그인 테스트 완료.
- 공유한 초기 비밀번호와 토큰은 이 문서에 기록하지 않습니다. 배포 전에 계정 소유자가 안전한 비밀번호로 변경해 주세요.
- 비밀번호를 바꾸면 기존 세션 무효화가 동작하는지 확인합니다.
- 운영자별 계정 사용을 권장합니다. 같은 계정을 공유하면 누가 환불·수정했는지 구분하기 어렵습니다.
- 현재 로그인 제한(429)은 유지하되 FE에서 '요청이 많으니 잠시 후 시도'로 분명히 안내합니다.
- 관리자 제거·비활성화 시 발급된 토큰으로 계속 접근할 수 없는지 확인합니다.

## 6. 추가·수정 요청 목록

### 6.1 PDF 열람과 다운로드 집계 분리

- 현상: 내려받기를 한 번 눌렀는데 관리자에는 2회로 표시.
- 원인 확인: FE에서 활동지 보기 진입 시 PDF GET 1회, 내려받기 클릭 시 다시 GET 1회. BE는 링크로 제공된 GET마다 기록.
- 현재 숫자는 '사용자가 저장한 횟수'보다 'PDF 제공/열람 요청 횟수'에 가깝습니다.
- 협의: 열람과 저장 요청을 분리 기록할지, 현재 의미에 맞춰 이름을 바꿀지 결정 부탁드립니다.
- FE 개선 후보: 이미 받은 blob을 저장에 재사용해 중복 파일 전송 감소.
- HTTP Range·브라우저 재시도·개발 모드 재실행이 기록을 늘리는지도 확인 필요.
- HEAD는 계속 집계 제외. 파일 생성 실패·권한 거절은 다운로드 성공으로 기록하지 않음.
- 실제 로컬 디스크 저장 완료를 서버 GET만으로 보장할 수는 없습니다.
- 환불 판단과 연결된 이력이므로 기존 기록을 임의로 삭제/축소하지 않습니다.

### 6.2 고객 주문 상세 응답 보완

현재 GET /orders/{id}에는 결제일·결제 수단 필드가 없어 FE가 날짜를 '서버에서 제공하지 않음'으로 표시합니다.

요청 필드 제안:

| 필드 | 의미 |
|---|---|
| created_at | 주문 생성 시각, ISO 8601 |
| paid_at | 결제/무료 주문 완료 시각, 미완료면 null |
| payment_method | 실제 결제 수단 또는 무료 주문 구분 값 |
| items[].image | 선택 사항. 주문 상품 표지 제공 시 별도 활동지 조회 감소 |

- 무료 주문을 토스 실결제로 표시하지 않습니다. FE는 현재 0원 주문에 '무료 주문' 표시로 수정했습니다.
- 응답 enum·null·과거 주문 처리 정책을 명세에 추가해 주세요.
- 고객 주문은 본인 것만 조회 가능해야 합니다. 관리자 주문 API를 고객 화면에서 사용하지 않습니다.

### 6.3 PDF 코드가 도안 이름 칸과 겹침

- 현재 BE 기본값: 모든 쪽 오른쪽 위, 12mm 여백, Courier 10pt.
- 명세에서 도안의 이름 칸과 겹치는 현상이 확인돼 있습니다.
- 관리자별/학습지별 위치·적용 페이지 옵션을 추가할지, 공통 도안에서 전용 코드 영역을 확보할지 협의 부탁드립니다.
- 조정 전 실상품 일괄 등록보다는 대표 도안으로 인쇄·사진 인식 테스트가 필요합니다.
- 원본 보존·회전 페이지·CropBox 처리 유지, 코드가 기존 내용을 가리지 않아야 합니다.

### 6.4 부모 프로필 추가 항목

- Figma: 이름·닉네임·아이와의 관계·연령대·이메일.
- 현재 API: name/nickname 저장 가능. 관계·연령대 필드 없음.
- 사용자 승인으로 지원 항목부터 연결했고, 관계·연령대는 아직 수집/저장하지 않습니다.
- 추가한다면 PATCH/GET /users/me의 필드·enum·선택/필수·null 처리 명세를 제공해 주세요.
- 휴대전화 본인인증 완료 이름 자동 입력 API도 없으므로 현재 이름은 직접 입력합니다. 인증 완료처럼 표시하지 않습니다.
- 가입 중 이탈 후 부모/아이 입력 재개가 필요하면 onboarding 완료 상태 API가 필요합니다.

### 6.5 아직 없는 기능

- 사진 인증 업로드·AI 결과·소유권/중복 판정·관리자 승인/반려 API
- 발급 코드 재발급·무효화 API (현재 조회만 제공)
- 카테고리 수정·삭제·연령/학년 트리 등 확장
- 문의·CS·프로모션·역할별 권한·관리자 감사 로그

우선순위를 합의해 진행하고, 없는 기능을 UI에서 완료된 것으로 표시하지 않습니다.

### 6.6 토스 결제 실연동 테스트

- FE에는 아직 동일 상점의 API 개별 연동 테스트 클라이언트 키(test_ck_...)가 필요합니다.
- BE 시크릿 키는 프론트·문서·Git 저장소에 전달하지 않습니다.
- 테스트 유료 상품으로 결제창 → BE 승인 → paid → 다운로드 권한 → 환불까지 검증합니다.
- 무료 주문으로 PDF 발급을 확인한 것은 토스 유료 결제 검증과 다릅니다.
